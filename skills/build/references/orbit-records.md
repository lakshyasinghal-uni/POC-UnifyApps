# Orbit records: where every POC document, decision and piece of feedback lives

Everything a POC produces lives in Orbit (orbit.uat.unifyapps.com), in three objects whose
definitions are in [orbit-objects.json](orbit-objects.json):

| Object | One row per | Key |
|---|---|---|
| `poc_studio_poc` | POC, however many sessions work on it | generated by Orbit: `POC-_1001`, `POC-_1002`, … |
| `poc_studio_document` | document version | `doc_id`: `<poc_id>__<stage>__<file-slug>__v<n>` |
| `poc_studio_feedback` | piece of feedback | `ticket_no`, generated by Orbit: `FB-_1001`, `FB-_1002`, … |

Nothing is ever deleted. A new version of a document supersedes the previous one by status.

The POC ID is never built from the client, the use case or the date: a row is created without
it (`new-poc`), and the ID Orbit returns is used everywhere. Client and use case are kept in
`client_name`, `client_slug`, `use_case_slug` and `poc_name` for search. (The early setup row
`POC-setup-test-20261015` keeps its manual ID.)

## Field names (the live tenant's)

The plugin writes only these names, which are the ones on orbit.uat. The objects themselves are
never changed by the plugin.

| Object | Fields the plugin writes |
|---|---|
| `poc_studio_poc` | **`client_name`**, **`owner_name`** (required; `poc_id` is generated), `client_slug`, `use_case`, `use_case_slug`, `poc_name`, `request` (the person's request, as typed), `owner_email`, `owner_slack_id`, `tier`, `demo_date`, `build_mode`, `stage`, `status`, `run_state`, `current_gate`, `g1_status`…`g4_status`, `resume_from`, `stall_reason`, `active_session`, `session_ids`, `last_heartbeat_at`, `started_at`, `last_activity` (one line), `last_activity_at`, `slack_destination` (the person's own Slack chat), `last_gate_thread` (the `ts` of the latest gate message), `tenant_host`, `solution_name`, `documents_count`, `open_feedback_count` |
| `poc_studio_document` | **`doc_id`**, **`poc`**, **`name`**, **`stage`** (required), `version`, `doc_type`, `gate`, `status`, `file`, `content`, `summary` (one line; it says which version this one replaces), `source_path` (the local file it came from), `file_url`, `size_bytes`, `created_by`, `created_at` |
| `poc_studio_feedback` | **`poc`**, **`feedback`** (the exact words), **`given_by_name`** (required; `ticket_no` is generated), `title`, `client_name`, `given_by_email`, `given_by_slack_id`, `channel`, `source_link`, `poc_stage`, `gate`, `category`, `severity`, `status`, `related_document`, `action_taken`, `created_at`, `resolved_at` |

`poc` and `related_document` are single-select references to another record: they hold that
record's id (for a POC row, the same value as its `poc_id`; for a document, its `doc_id`).
`save-doc` and `new-ticket` fill them; never type them by hand.

The app's link has no field of its own: it goes in the G3 gate pack and in `last_activity`.

**The schema check.** `schema-check` reads the three live schemas and compares them with these
names and with every single-select value the plugin writes (stage, status, gate, tier,
run_state, build_mode, doc_type, category, severity, channel and the gate statuses). Setup and
the start of every build run it. When anything differs it exits 5 with the exact list (a field
the tenant does not have, a field the tenant requires that the plugin never writes, values that
are not options) and the run stops there: show the list to the person, and do not rename fields
or change values to make a write pass. Every write is checked the same way before it is sent, so
a write that does not match stops with exit 5 and writes nothing.

## Two ways to reach Orbit

**1. Direct API, no browser (preferred).** `node "${CLAUDE_PLUGIN_ROOT}/scripts/orbit-api.mjs"`
with the session in environment secrets: `ORBIT_COOKIE`, or `ORBIT_USERNAME` and
`ORBIT_PASSWORD` for a local account. Never ask for these in the chat and never print them.
Every command prints one JSON line. Exit 0 is done, 1 is an error, 3 is "not reached Orbit,
queued" (`reconnect: true` means the session itself has gone), 4 is "another session holds
the POC", and 5 is "the live schema does not match" (stop and show the list).

| Command | Use |
|---|---|
| `check` | Who is signed in; whether the three objects exist; `userMismatch` when it is not the user setup recorded |
| `schema-check` | Compare the live schemas with the fields and options the plugin writes; exit 5 with the list when they differ |
| `selftest [--poc <id>]` | On the real tenant: the schema check, then a write and a read-back on all three objects and one file upload and download; prints a results table |
| `ensure-objects` | Create any missing object from orbit-objects.json; an existing one is never altered |
| `refresh-schemas` | Replace the schemas in orbit-objects.json with the tenant's live ones, and list every field and its options |
| `new-poc <json or @file>` | Create a POC row; Orbit generates `poc_id`, which the output returns |
| `find-poc <text>` | POCs whose ID, name, client or use case match, newest first, with stage, run state, build mode, resume point and last activity |
| `claim --poc --session [--force]` | Take the row for this session; exit 4 when another session's heartbeat is under 2 hours old |
| `heartbeat --poc --session [--run-state] [--resume-from] [--stall-reason] [--stage] [--current-gate] [--activity]` | Keep the run fields current; `--activity` is the one line shown as `last_activity` |
| `fetch-doc --poc --slug --out` | The latest version of a document back to a local file (its text, or the uploaded file) |
| `schema <object>` | The live object definition (to refresh orbit-objects.json) |
| `get <object> <id>` · `find <object> --field f --value v --limit n` | Read |
| `create <object> <json or @file>` | New row, with the field names above. Pass anything holding a person's words as `@file`, so the words never sit in a shell command |
| `update <object> <id> <json or @file>` | Read the row, merge the given properties, write the full record with its version |
| `upload <path>` | Upload a file; returns the File-field value. The bucket and directory come from `GET /api/file/upload-bucket` (`ORBIT_BUCKET` overrides the bucket only) |
| `save-doc --poc --stage --slug --name --type --file [--status] [--gate] [--summary] [--by]` | Upload the full file, create the next version (text also in `content` up to ~1 MB), mark the previous one `superseded`, update the POC's `documents_count` and `last_activity`. `--name` is the document's title |
| `new-ticket --poc --feedback @file --title [--by-name] [--by-email] [--by-slack-id] [--stage] [--gate] [--category] [--severity] [--doc <doc_id>] [--source-link]` | A feedback ticket; returns the `ticket_no` Orbit generates. Without `--by-name` it is the signed-in person |
| `close-ticket --ticket <ticket_no> --action <what was done> [--status done\|wont_do]` | Close a ticket: `status`, `action_taken`, `resolved_at` |
| `readback --poc <id>` | Every latest document: file uploaded, version, status; `ok` only when all are there and nothing is queued |
| `sync-counts --poc <id>` | Recompute the POC row's `documents_count` and `open_feedback_count` from the records |
| `flush` | Replay queued writes in order. It stops at the first that cannot reach Orbit yet; one that can never succeed (its local file is gone, or Orbit rejects it) is skipped, moved to the `.dead.jsonl` file beside the queue, and raised as a feedback ticket |

**2. A signed-in Orbit tab.** When no secret is set, use a browser tab already signed in to
Orbit (the built-in browser first, then Claude in Chrome) and run the same calls same-origin
with the browser's JavaScript tool. The cookie rides along and nothing enters the chat. Paste
these two helpers once per tab:

```js
// ps: one call to Orbit from a signed-in tab. ps('GET', '/api/user-context')
window.ps = async (method, path, body, headers = {}) => {
  const r = await fetch(path, { method, credentials: 'include',
    headers: { Accept: 'application/json', ...(body ? { 'Content-Type': 'application/json' } : {}), ...headers },
    body: body ? JSON.stringify(body) : undefined });
  const t = await r.text();
  if (r.status === 401 || (r.headers.get('content-type') || '').includes('text/html')) throw new Error('Orbit session expired');
  if (!r.ok) throw new Error(`${method} ${path} -> ${r.status}: ${t.slice(0, 200)}`);
  return t ? JSON.parse(t) : null;
};

// psUpload: upload a File or Blob the way the Orbit UI does; returns the File-field value.
window.psUpload = async (file, name = file.name, mime = file.type || 'application/octet-stream') => {
  const { bucket, directory } = await ps('GET', '/api/file/upload-bucket'); // read from the tenant, never hardcoded
  const h = { 'x-ua-uppy-upload': JSON.stringify({ useExternalApi: false,
    bucketDetails: { directory, bucket }, isPublicUpload: false, isBuilderAsset: false }) };
  const { uploadId, key } = await ps('POST', '/api/uploads/s3/multipart', { filename: name, type: mime, metadata: { name, type: mime } }, h);
  const PART = 8 * 1024 * 1024, parts = [];
  for (let n = 1, off = 0; off < file.size || n === 1; n++, off += PART) {
    const { url } = await ps('GET', `/api/uploads/s3/multipart/${uploadId}/${n}?key=${encodeURIComponent(key)}`, null, h);
    const put = await fetch(url, { method: 'PUT', body: file.slice(off, off + PART) });
    parts.push({ PartNumber: n, ETag: put.headers.get('etag') });
    if (off + PART >= file.size) break;
  }
  const done = await ps('POST', `/api/uploads/s3/multipart/${uploadId}/complete?key=${encodeURIComponent(key)}`, { parts }, h);
  const source = done?.key || key;
  const fileDetails = { fileType: mime, name, size: file.size, source, sourceType: 'CLOUD_STORAGE', 'ua:type': 'FILE' };
  const { url } = await ps('POST', '/api/file/signed-url?preview=true&expiryTime=1', { fileDetails });
  return { name, source, sourceType: 'CLOUD_STORAGE', mimeType: mime, fileType: mime, size: file.size, type: 'FILE', url };
};
```

A document saved from a tab follows `save-doc`'s steps by hand, with the field names above: find
the latest version for the POC (filter `properties.poc`) and the slug (read from `doc_id`),
`psUpload` the file, `ps('POST', '/api/entity', {entityType:
'poc_studio_document', properties})`, set the previous version's status to `superseded`
(`ps('POST', '/api/entity/update', …)` with the full properties and its `version`), then update
the POC row's `documents_count`. Check the values against the live schema first (`ps('GET',
'/api/entity-type?entityType=poc_studio_document')`); stop on any difference. A file made in the workspace reaches the tab through the
browser's file upload, never by pasting its bytes into the chat.

## The write-back check (before every human step)

Before any gate is sent, and before any other question reaches a person:

1. `flush`. A skipped write comes back with its ticket number; say it in one line and go on.
2. Save every document made since the last check with `save-doc`, and every working document
   that changed (run-control.md § Working documents), with the `run-log`.
3. `readback --poc <id>` and confirm each document this POC has made so far is there: full
   file uploaded, latest version, status as expected.
4. Update the POC row: stage, status, current gate, counts (`sync-counts`), and the run fields
   with `heartbeat` (`run_state`, `resume_from`, `stall_reason`, `active_session`,
   `last_heartbeat_at`).

When any step does not reach Orbit (exit 3, `reconnect: true`, a missing document, or a
`userMismatch`), stop and set `run_state: stalled` with `stall_reason: Orbit not reachable`
if the row can be written. Tell the user in one line what did not save and how to reconnect: sign
in to Orbit again, set `ORBIT_COOKIE` again, or open Orbit in the browser for them to sign in.
Do not send the gate or start
the next step until the check passes. After a gate answer, write the decision (a
`gate_decision` document and the POC row's gate status) and run the check again before the
next phase starts.

## Feedback tickets

Every piece of feedback in the chat, at any time, becomes a `poc_studio_feedback` row through
`new-ticket`: the exact words in `feedback` (passed as `@file`), a short `title`, who gave it
(`given_by_name`, `given_by_email`, `given_by_slack_id`), the stage (`poc_stage`) and gate, a
category and severity, and the document it is about (`--doc`, filling `related_document`).
Feedback the owner gives is theirs to rule on; something they pass on from someone else is
noted as such at the start of `feedback`. Acknowledge it with its `ticket_no`. Close it with
`close-ticket`: `status: done` (or `wont_do`) and one line in `action_taken` saying what was
done. The POC row's `open_feedback_count` follows.
