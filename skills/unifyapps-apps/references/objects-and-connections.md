## Objects (Data Objects)

An object is an **`EntityType`** (aggregation group `STANDARD`). Its id is either what you pass
(`maher_scratch_task`) or generated (`obj_<5 chars>` for agent-created ones); `name`/`lcName` are the
display names. Its records are entities whose `entityType` is the object id. ~18,300 custom
objects on UAT.

### Endpoints

| Step | Call | |
|---|---|---|
| Create | `POST /api/entity-type` `{id, name, pluralName, description, metadata:{storeDetails:{store:"MONGO"}}, tags:[]}` | ✅ |
| Read one | `GET /api/entity-type?entityType={id}` | ✅ |
| Read many | `POST /api/lookup?ByKeys=ENTITY_TYPE` `{type:"ByKeys", lookupType:"ENTITY_TYPE", keys:[ids]}` | ✅ |
| Update schema / settings | `POST /api/entity-type/update` — the **full** object as read, with `input` and `schema` set | ✅ |
| Custom indexes | same update, `metadata.customIndexDefinitions` — see §"Indexes" | ✅ |
| List objects | `POST /api/aggregation?entityType=EntityType&group=STANDARD` (filter `standard` false/MISSING for custom; project `name,id,columns,tags,oUId,cTm,mTm`) | ✅ |
| Field metadata | `POST /api/lookup?ByQuery=ENTITY_FIELD` `{options:{group:"ENTITY", entityType}}` or `POST /api/aggregation/metadata?entityType={id}&group=ENTITY` | ✅ |
| Permissions | `POST /api/lookup?ByKeys=ENTITY_PERMISSIONS` `{options:{entityType:"ENTITY_TYPE"}, keys:[id]}` | 👁 |
| Import history | `POST /api/entity/e_file_import_details` filter `properties.entityType` | 👁 |

Dead ends: `GET /api/entity-type/{id}` 404, `/api/entity-type/find/{id}` 404,
`/api/entity-type?id=` 500, `lookup?ByKeys=EntityType` 5004 (*Lookup type not supported*).

UI store types on create: JSON Store (`MONGO`), Blob Store, Key Value Store, Event Store, Vector
Store, Analytics Store; plus Retention period, Workspace, Tags, and toggles Enable reporting /
activity tracking / audit trail / external access. Only `MONGO` has been exercised.

### Schema format

`input` and `schema` carry the same JSON Schema:

```json
"input":  {"type":"SCHEMA_AND_LAYOUT", "schema": <S>, "layout": {"ui:order": ["task_code","title",...]}},
"schema": {"dynamic": false, "type": "SCHEMA", "schema": <S>}

<S> = {"type":"object", "additionalProperties": false, "required": ["task_code","title"],
       "properties": {
  "task_code":      {"type":"string","title":"Task Code","help":"Business key","primaryKey":true,"nameField":true,"uniqueKey":false,"searchable":true,"sortable":true,"filterable":true},
  "title":          {"type":"string","format":"text","title":"Title"},
  "status":         {"type":"string","format":"single-select","default":"open","oneOf":[{"const":"open","title":"Open"},{"const":"done","title":"Done"}]},
  "estimate_hours": {"type":"number","title":"Estimate (h)"},
  "is_blocked":     {"type":"boolean","title":"Blocked?"},
  "due_at":         {"type":"integer","format":"date-time","dateFormat":"epoch","title":"Due At"},
  "email":          {"type":"string","format":"email"},
  "task_no":        {"type":"string","format":"auto-generate","autoGeneratedFieldDefinition":{"prefix":"TSK-","startFrom":1001},"primaryKey":true,"uniqueKey":true},
  "category":       {"type":"string","format":"single-select","foreignKey":{"reference":"ENTITY_ID:<targetObjectId>"}}
}}
```

- UI field types: String, Number, Integer, Auto Number, Boolean, Date, Date Time, Single/Multi
  Select Dropdown (static `oneOf` or a Lookup `foreignKey`), Object, Array, File; Vector/Geo Point
  for vector stores. Advanced: hashing, secure (encrypted) field, display name, search/sort/filter, visibility conditions.
- The server **derives `metadata`** from the per-field flags on save: `primaryKeyField`,
  `nameField`, `uniqueKeyFields`, `searchableFields`, `filterableFields`, `dateFields`,
  `autoGeneratedFields`, `referenceKeys` (from `foreignKey`). You set flags, not metadata.
- A lookup field stores the target record's `id` (array of ids for multi-select). Foreign keys
  are only checked if enforced; nothing cascades.

### Records — what else was verified (a multi-agent build, UAT 2026-09-25) ✅

- **Aggregation on records needs `projections`** — `POST /api/aggregation?entityType={obj}&group=ENTITY`
  without it is a 500 (`"projections" is null`). No group-by / SUM / COUNT shape tried grouped anything
  (each returned one row per record). Compute KPI totals in a workflow Groovy step over a full storage
  fetch (≤ 2,000 rows) and return numbers; never reduce a page in the app. `POST /api/entity/{obj}`
  returns `objects, cursor, hasMore` — **no total**.
- **Renaming a field**: replace the property in BOTH `input.schema` and `schema.schema` (keep
  `ui:order`), `entity-type/update`, then rewrite every record with a **full** body via
  `POST /api/entity/update`; check `distinctKeys` over a full read that no row still carries the old key.
- **The replace guard needs a per-batch allow-list**: when a new mapping legitimately clears a field
  (`health_reason` on green rows, `completed_at` when a milestone leaves `done`), pass
  `allowDrop:['health_reason']` for that batch — every other missing key stays a hard error.
- **Idempotent reload**: create → on `E11000` read the row's `version` → `entity/update` with the full
  body. 1,252 creates with 8 workers ≈ 10 s; full-row equality against the generator = the final check.
  Reference: `SC-Companion-Agents/work/run-002-*/data/{schemas.js,generate-seed.js,load-seed.js,model.md}`; API-SPEC §48.

### Indexes — every object gets the ones its queries need ✅ UAT 2026-09-28 (TAQA `taqa_kpi`, `taqa_document`)

Only the **primary key and unique keys** are indexed automatically (`PK_<field>`, `UK_<field>`).
The `filterable` / `sortable` / `searchable` flags **do not create indexes**. They only let the UI
filter and sort. So every filter or sort on another field reads the whole collection. TAQA shipped 16
objects with 7–58 filterable fields each and no index at all besides the key.

Custom indexes are part of the object's metadata. The UI (Objects → object → Settings → Object Indices)
and REST write the same thing:

```js
const et = await (await fetch(`/api/entity-type?entityType=${id}`)).json()   // full object, incl. `schema`
et.metadata = { ...et.metadata, customIndexDefinitions: [
  { name: 'index_1', indexFieldMetadataList: [                               // compound: order matters
      { field: 'properties.scope',  type: 1 },                               // 1 = ASC, -1 = DESC
      { field: 'properties.metric', type: 1 },
      { field: 'properties.period', type: 1 } ] },
] }
await fetch('/api/entity-type/update', { method: 'POST', headers: { 'content-type': 'application/json' },
                                         body: JSON.stringify(et) })
```

- The reply carries `status: "IN_PROGRESS"` per index. Re-read until every index is **`SUCCESS`**
  (seconds at 5k rows). Check `columnCounts` is unchanged and `version` went up by one.
- **At most 5 custom indexes per object** (UI `MAX_CUSTOM_INDEXES`). Names have no spaces; use `index_1…5`.
  Send the full list every time: the array replaces the previous one.
- **What to index:** the queries the app, its data sources and its workflows actually run, one
  compound index per query shape, fields in **equality → sort → range/IN** order:
  `supplier_code EQUAL` + sort `days_to_expiry` → `{supplier_code:1, days_to_expiry:1}`;
  `status IN` + the same sort → `{status:1, days_to_expiry:1}`. A foreign-key field that screens
  filter on (`supplier_code`, `event_code`) always gets one. A sort-only list that will grow gets
  its sort field. Don't index what the key already covers. Small bounded reference tables
  (categories, scenarios, stories) don't need an index.
- **Rows with equal sort values can come back in a different order** after indexing (same rows,
  still sorted). Code must not depend on tie order. Add a second sort field when order matters.
- Measured on TAQA: the same queries returned the same rows at the same speed (43–59 ms median,
  mostly network) at 4.5–5.4k rows. The index matters as the data grows. It doesn't make a small
  object faster, so don't promise a speed-up; report it as done.
- Rollback = the same update with the previous `customIndexDefinitions` (or `[]`). No records are touched.

## Where each system's data comes from — connect, simulate or collect (ported 2026-09-28)

Every outside system in a use case gets one of three modes, chosen with the user (build question B4). Record the
mode per system in the build notes and the report.

| Mode | When | What gets built | What the user sees |
|---|---|---|---|
| **connect** | a usable connection exists, or the user will create or authorize one | connector nodes with `context.connectionId`; tests read real data | real data, with a lineage chip naming the source |
| **simulate** | no usable connection yet (the default then) | an object shaped like the source's output, with labelled sample rows (playbook `build-options.md` "The seed rule"); the workflow reads the object through the **same field names** the connector would return | "Sample data" beside every block that renders it; listed in the report |
| **collect** | the data does not live in a system yet (uploads, forms, forwarded emails) | FileUpload or Form → workflow → object; no seed (`unifyapps-config-apps/references/documents.md`) | empty until real input arrives; tests use uploaded files |

Switching simulate → connect later must be a change of the reading node (connector instead of storage fetch) and
nothing else, so design the simulated object to make that true. The full pattern for simulating a system (a
simulator workflow, a sync workflow and the real integration beside it) is `ai-app-patterns.md` §22.

### 🔴 `useRawPayload` REPLACES the record — a partial payload silently deletes every other field

❌ **Learned the expensive way, 2026-09-23.** All five write bindings (`CREATE`, `UPDATE`,
`UPSERT`) carry `useRawPayload: true` as a *stored* input. It is not a merge. Send

```js
UA.update('<uc>_supplier', 'SUP-1439', { risk_score: 58, risk_band: 'HIGH' })
```

and the record becomes **exactly those two fields**. Name, spend, governorate, coordinates,
scores — gone. It returns **200**. Nothing warns you.

What it does do — and this is the only reason the damage was noticed — is validate the result
against the object's schema, so the first attempt failed 90/90 with
`Non Empty Validations … required supplier_code`. **That error is not a nuisance to route around
by adding the missing key. It is the platform telling you the write is a REPLACE.** Adding
`supplier_code` to the payload silenced the validator and stripped 415 records to five fields.

**The rule: never hand a write binding anything but the whole record.**

```js
// The only safe shape. Read, spread, change, write back.
const row = (await UA.fetchAll('<uc>_supplier', { limit: 1, where: byCode('SUP-1439') }))[0]
await UA.upsert('<uc>_supplier', row.id, { ...row.properties, risk_score: 58, risk_band: 'HIGH' })
```

**The same applies inside the code app.** The app's `useRecordWriter().update(object, id, changes)`
must BE this read-merge-write (FETCH the row by `id` through the FETCH binding's full stored set,
spread `properties`, apply `changes`, then UPDATE), so screens can pass partial changes safely.
❌ 2026-09-25, a supplier-risk build: the in-app writer passed `changes` straight through as
`rawPayload`. The first "Save pack" on a new object failed `required review_code`; adding the key
(the trap above, again) made the next save strip the review to three fields. Older objects without a
required key would have been stripped silently on every status change. Audit after any writer
change: count records per object with fewer than ~5 non-empty fields.

Add the guard to the helper itself so it cannot be forgotten at a call site:

```js
/** A write that is missing fields the record already has is a REPLACE that deletes them.
 *  `useRawPayload` gives no merge and no warning, so the check lives here. */
async function patch(objectType, id, changes, { expectFields } = {}) {
  const row = (await exec('FETCH_ONE', { object_type: objectType, triggerInputCondition: eq('id', id) }))
    ?.response?.objects?.[0]
  if (!row) throw new Error(`${objectType}/${id} not found — refusing to write`)
  const next = { ...row.properties, ...changes }
  const lost = Object.keys(row.properties).filter((k) => !(k in next))
  if (lost.length) throw new Error(`refusing to drop ${lost.length} field(s): ${lost.join(', ')}`)
  if (expectFields && Object.keys(next).length < expectFields) {
    throw new Error(`payload has ${Object.keys(next).length} fields, expected >= ${expectFields}`)
  }
  return exec('UPDATE', { object_type: objectType, recordId: id, rawPayload: next })
}
```

### 🔴 Before ANY bulk write, take a snapshot you can restore from

A deterministic seed is a recovery plan — `T.writeSuppliers(440)` rebuilt all 440 records exactly,
which is the only reason this was a twenty-minute problem instead of a rebuild. But it only covers
records the seed generates. Anything written since (a scenario applied, a user's edit, an action
raised) is not in it.

So, before a bulk write, and it costs one line:

```js
const snap = await UA.fetchAll(objectType, { limit: 500 })
copy(JSON.stringify(snap))            // or download it — see "Export the automations into the repo"
```

and a restore is `UA.pool(snap, 12, r => UA.upsert(objectType, r.id, r.properties))`.

### 🔴 Dry-run the first record, read it back, THEN run the batch

```js
const [first, ...rest] = plan
await patch(objectType, first.id, first.changes)
const after = await readOne(objectType, first.id)
console.log(Object.keys(after.properties).length, 'fields')   // must match the snapshot's count
```

415 records were stripped because the loop ran to completion before anything was read back. The
harness reported `done: 415, failures: 0` and every one of those "successes" was a deletion. **A
2xx from a write binding proves the call was accepted, never that the record is still whole** —
verification is a READ, and the cheapest useful assertion is a field count.

### 🔴 Verify a repair the same way you verify a build

After restoring, check the numbers that existed before, not just the row count:

| Check | Why |
|---|---|
| `count(objectType)` | rows are back |
| min fields per record | **the one that catches a replace** (62 here, not 5) |
| a business total (`exposure: EGP 934.64m`) | the same figure as before the damage = the values are right, not just present |
| the derived vocabulary mix | 205/155/74/6 — the distribution, not a spot check |
| apply + reset one scenario, diff the fingerprint | the baselines survived the repair |

### Tell the user immediately

The damage was found by reading back a field that came out `undefined` in an unrelated check. Say
what broke, what is recoverable and how, and ask before the repair — do not quietly repair and
mention it afterwards. A silent fix removes the user's chance to say "stop, I have a backup" or
"leave it, I'll re-seed tonight".

## Four ways the platform answers 200 and does nothing ✅ a document-fraud build, UAT 2026-09-23

All four were found by *running* the thing and counting rows, never by reading a response. Add
them to the list you check first when an automation "worked" and the data did not move.

### 1. A bulk upsert whose `updates` carry `properties` instead of `updateFields`

`storage_by_unifyapps_bulk_upsert_records_by_id` takes **field-level** edits:

```jsonc
{ "object_type": "<uc>_claim", "skipIfBlank": false, "unsetIfNull": false,
  "updates": [ { "id": "<record id>",
                 "updateFields": [ { "fieldName": "risk_score", "actionType": "SET", "setValue": 74.6 } ] } ] }
```

Send `{id, properties:{…}}` — the shape `POST /api/entity/update` wants — and the run succeeds,
the STOP node reports the row count your Groovy built, and **nothing is written**. Always read one
record back after the first batch; never trust the count the automation returns.

(The field-level shape is a genuine partial update, so unlike `useRawPayload` on the create node
it does not silently strip the fields you left out.)

### 2. A fetch node read through `outputs.records`

The collection a `storage_by_unifyapps_fetch_records` node emits is **`{{ n_x.outputs.objects }}`**.
`outputs.records` resolves to nothing, the downstream Groovy sees an empty list, and the workflow
happily returns zero of everything.

### 3. A fetch node with no `triggerInputCondition`

Omit it and the node returns nothing at all. To fetch every record, send it empty:
`triggerInputCondition: {}`. `page: {paginateBy:'OFFSET', limit: 2000, offset: 0}` returned
everything at low thousands of rows.

### 4. A data source called without all of its templated inputs

A data source whose stored inputs contain `{{placeholders}}` must be sent **every one of them**,
blank where unused. Leave one out and the placeholder reaches the workflow as literal text and it
filters on the string `{{filter_field}}`:

```js
// <uc>_query declares 15 parameters. This returns count: 0 on an object holding 8 rows.
runDS(QUERY_DS, { object_type: '<uc>_school', limit: 50 })

// This returns 8.
runDS(QUERY_DS, { object_type: '<uc>_school', limit: 50,
  filter_field: '', filter_value: '', filter_field2: '', filter_value2: '',
  filter_field3: '', filter_value3: '', sort_field: '', sort_order: '', fields: '',
  name_contains: '', min_field: '', min_value: '', max_value: '' })
```

This is the read-side twin of `500 forbidden datasource : invalid input`. On a write the platform
tells you; on a read it just answers zero.

### And one that does fail loudly, for completeness

A START node created over the API without `trigger: {type: 'CALLABLE'}` makes
`saveAndReturnViolations` 500 with `Node.getTrigger() is null`. Note the preceding
`POST /api/workflow-definition` **succeeded**, so the workflow already exists — fetch it, add the
trigger, and save that rather than re-running your builder and minting a second one.
